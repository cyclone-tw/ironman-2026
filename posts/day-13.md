# Day 13｜AI 說我錯了，我拿實驗反駁它

昨天寫到 [`cyclone-hermes` PR #140](https://github.com/cyclone-tw/cyclone-hermes/pull/140) 第二輪審查。這一輪裡有一條 finding，發展成整個系列我反覆想起來的一課。

先講場景。我的升級前檢查腳本裡有一段工作很簡單：找出最近 36 小時內產生的備份檔，確認備份流程真的有在跑，不是三天前就斷了。實作用的是 `find`——一個 unix 平台人人內建的標準工具——加上「36 小時」的條件，當時寫成 `-mtime -36h`，結尾那個 `h` 代表小時。

第二輪審查時，reviewer 指出：這種小時寫法只在 Linux 上有效，macOS 上同名同姓的那個標準工具不認得 `h`。意思是，這一行在我自己每天在用的機器上會直接掛掉，而我寫的時候以為它沒問題。

照一般的做法，我可以有兩種反應。第一種是聽話：reviewer 說會掛，那就不辯了，直接改成別的寫法，求個平安。第二種是嘴回去：胡說，這個我在 BSD 系統上明明用過，你才是錯的。

兩種我都沒有做。兩種都是用人對人說話的方式：一種是把判斷直接讓給它，一種是把嗓門拉高。一來一回各自堅持，最後誰也沒有推動真相。

## 先跑，再回答

我採取的是第三種：不要先回答，先去跑。

我進到那台實際會執行這段程式的機器，把有爭議的指令原封不動打進去，看回傳什麼。結果：

```text
find 指令 exit code 0，正確列出兩個備份檔
```

指令在它說會掛掉的平台上，正常執行，一次不差地列出我要找的兩個備份檔。reviewer 的技術判斷錯了。

我在 PR 留言裡把結果寫了回去：**實驗反證**，mini 上實跑該指令 rc=0 並正確列出兩個備份檔。也就是說 macOS 自帶的那個版本接受小時寫法，這一條 finding 不成立。

## 反駁成功，我還是改了

這裡是整件事最有意思的部分。

我實驗贏了，這條 finding 沒有站得住。但接下來這段程式碼我還是照它原本的建議，把小時寫法換成了 `-mmin`——另一種 GNU 和 BSD 兩邊都認得的寫法。

原因很簡單：反駁成功只證明了「今天在我這台機器上不掛」，證明不了「明天把腳本搬到別的機器上也不掛」。那個小時寫法是 macOS 端的擴充功能，不是標準的一部分；`-mmin` 是兩個平台都內建的正式語法。

白話一下這個決定：reviewer 說「這行會掛」，我證明「這行不會掛」，然後我還是換了寫法。表面上看起來是我贏了那場辯論，卻做了它建議的事，好像白吵一場。不是。辯論的輸贏歸辯論，選哪種寫法歸另一個更寬的標準：不靠今天剛好跑得動，只靠到哪裡都跑得動的工具。

這一次，實驗先救回了真相，再幫我做出更好的選擇。

## 講道理是誰最後說了算

這次攻防裡，最後的裁決由三個角色分工：reviewer 負責指出問題，但它的判斷可以被反駁；我負責反駁，但只能用可以重現的實驗反駁，不能多說一句理由；最後裁定的，是跑出來的結果本身。

不是 AI 說了算，也不是人說了算，是證據說了算。

同一輪還有兩條 findings：一條有理，修了安裝程序的驗證範圍；一條是小瑕疵，也順手處理。這兩條都沒有走到「反駁」這一步，安靜地修掉了。但這兩天想拉出來的真正故事，就是那條小時寫法：一個 review 流程最理想的樣子，不是大家都不吵架，而是有一個放證據的地方，讓每一場爭執最後都落地成實驗。
