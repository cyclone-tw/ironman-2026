# Day 13｜AI 說我錯了，我拿實驗反駁它

昨天寫到 [`cyclone-hermes` PR #140](https://github.com/cyclone-tw/cyclone-hermes/pull/140) 第二輪審查。這一輪裡有一條 finding，發展成整個系列我反覆想起來的一課。

reviewer 看我新加的升級前檢查，指出一段程式碼寫的是 `find -mtime -36h`，用到了小時單位（`h` 後綴）。它說這是 GNU find 的寫法，macOS 的 find 不支援，也就是說這一段在我自己每天在用的機器上會直接失敗。

照一般的做法，我可以有兩種反應。第一種是聽話：reviewer 說不支援，那就不支援，直接改成別的寫法，求個平安。第二種是嘴回去：胡說，這個我在 BSD 系統上明明用過，你才是錯的。

兩種我都沒有做。因為兩種都是用人對人說話，一來一回，各自堅持，最後誰也沒推動真相。

## 先跑，再回答

正確的第三種反應是：不要回答，去跑。

我進到那台實際會執行這段程式的機器，把有爭議的指令原封不動打進去，看回傳什麼。結果：

```text
find 指令 exit code 0，正確列出兩個備份檔
```

指令在它說會失敗的平台上，正常執行，正確列出我要找的兩個備份檔。reviewer 說錯了。

我在 PR 留言裡把結果寫了回去：**實驗反證**，mini 上實跑該指令 rc=0 並正確列出兩個備份檔，也就是說 macOS 自帶的 BSD find 接受 `h` 後綴，這一條不成立。

## 反駁成功，我還是改了

這裡是整件事最有意思的部分。

我反駁成功了，reviewer 也接受了這條 finding。但接下來這段程式碼我還是照 reviewer 的建議，把 `-mtime` 改成了 `-mmin`。

原因是在 PR 留言裡寫清楚的那個：`-mmin` 是 GNU 和 BSD 兩邊都支援的寫法，`-mtime` 的 `h` 後綴靠的是 BSD 特有的擴充。我的審查腳本未來可能搬到其他平台執行，我不想要一段只有在某種 unix 上跑得動的程式，只因為它今天剛好跑得動。

白話一下這個決定：reviewer 說「這行會掛」，我證明「這行不會掛」，然後我還是換了寫法。表面上誰都贏也誰都輸不是重點，重點是證據當場跳了兩次：第一次跳掉 reviewer 的推測，第二次跳出一個更好的設計選擇。如果沒有人去跑那個實驗，留下來的會是錯的──只有「聽話的我」和一個無意義的防禦性重寫。

## 講道理是誰最後說了算

這次攻防裡，最後的裁決由三個角色分了工：reviewer 執行其判斷，但它的判斷可以被反駁；人（我）可以反駁，但只能用可重現的實驗反駁；最後裁定的是跑出來的證據本身。

不是 AI 說了算，也不是人說了算，是證據說了算。

同一輪還有兩條 findings 沒有走到這個階段──一條是有理的（修了安裝程序的驗證範圍），一條是小瑕疵。但是這兩天想拉出來的真正故事就是那條 `-mtime`：一個自動化 review 流程的最高境界常常不是少吵架，而是有一個地方可以放證據，讓大家的推測都開始可以協作。
