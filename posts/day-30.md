# Day 30｜一個人的工程系統，和還沒解的問題

連載的最後一天。前二十九天我寫了一整套系統的細節，收尾這一篇做兩件事：把整個故事壓縮回它一開始的形狀，然後誠實列出還沒解的問題。

## 這三十天其實只講了一件事

回頭看，這個系列的主軸從第一篇到最後一篇沒有變過：**AI 會告訴我「做完了」，而我需要它拿證據。**

「做完了」是一個宣告。宣告可以錯、可以因為模型的樂觀偏差而失真、可以在說與被說的兩邊都不自覺。三十天裡的每一個機制──可驗收的 issue、垂直切片、跨 agent 的審查、工作帳本、隱私閘門──全部都是同一個設計問題的不同切面：**把「宣告」和「證據」分開，讓宣告不夠格的時候，證據可以說話。**

而這些機制沒有一個是我想出來的，全部是事故逼出來的。撞車逼出帳本、鎖死逼出人工出口、symlink 逼出載入驗證、人名全刪逼出處置表。如果這個系列有一個統一的方法，那就是：**每次事故之後，把當時的判斷寫成規則，讓下一次不用重新判斷。**

## 這個系統是誰的

定位要誠實：這是一個國小教師一個人的工程系統。它的單一用戶是我自己，它的規模就到我的兩台電腦加幾個雲端訂閱。它不是能直接搬進公司的方案，也不是團隊流程的示範。

也因此裡面的數字都是「為一個人量身」的。切片大小對應一個人的 review 注意力；輪次預算對應一個人的費用上限；紅線對應教師工作的資料種類。這些數字換一個人就會變。**可以帶走的是原則，不是參數：每個宣告要有證據、每個證據要能重跑、每個紅線要由入口把關。**

## 還沒解的問題（誠實清單）

Day 03 發現的規則缺口，至今仍未裁決：無人值守出貨的條件寫著「CI 綠」，但放這條規則的 repo 自己沒有 CI，規則也沒定義這個情況。我刻意沒有在系列中途把它寫成已解決。它現在還在。

費用側的控管還是「事後看」，沒有「事中擋」。預算目前完全靠我每天看一眼帳單。

隱私的語意層還是靠我逐字讀。自動閘門能抓的只有機械字串，「指向某人某校的描述」仍然只有人能判斷。這個職務目前是我在扛，我還沒有找到可以放心委外的方案。

紀律問題也有一個：拆切片的規則寫出來了，但我自己偶爾還是會為了趕一個完整功能直接推出大幅 diff，然後在最後的 review 跟它對打。這不是系統的洞，是我自己的洞，但我把它和系統的洞列在一起，因為兩者都該被看見。

## 三十天的成本與賺到的

成本是真實的：三十天、每天一篇、頭三個星期是白天工作晚上拚稿。這裡不用形容詞，講一個可核算的：這個系列寫完，這個 repo 會有三十個 `evidence/` 目錄，每一個都對應一天我可以自己重跑的驗證，加上每篇引用的全部 GitHub issue 與 PR。**一篇文一個單位的可重跑證據**，這是我給自己的鐵律，也是這個系列和「講心得」類文章的最大差別。

## 明天

沒有明天了。剩下的路是把清單上還沒解的問題，一個一個變成新季度的 issue。鐵人賽在這裡結束，工作本身繼續。
